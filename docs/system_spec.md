# システム仕様

- 文書ID：SPEC-DOC-001
- 状態：初版・技術検証前
- 関連要求：REQ-INPUT-001, REQ-BIND-001, REQ-MOD-001, REQ-PASS-001, REQ-ARCH-001, REQ-QUEUE-001

## 1. 目的と範囲

複数のHID入力デバイスをAHIで受け取り、AHK v2のアプリケーション処理で組み合わせる。入力の組み合わせ例は、フットスイッチによるテンキー機能の切替、および別キーボードの修飾キー状態に応じた入力動作の変更である。

この文書は初期の論理仕様を定める。AHIの実際のフック挙動、抑制可否、タイミング、同時入力処理は技術検証が終わるまで確定しない。

## 2. 論理構成

1. **入力ドライバ層**：AHIの入力フックを受け、デバイスとキーイベントを識別する。
2. **イベント受け渡し層**：入力イベントを構造化し、アプリ処理側へ渡す。
3. **修飾キー管理層**：デバイス横断の修飾キー状態を管理する。
4. **キーバインド処理層**：現在の入力イベントと修飾キー状態、設定済みバインドを用いて動作を決定する。
5. **実行・診断層**：決定されたアクションを実行し、必要最小限の診断情報を扱う。

## 3. 基本フロー（論理）

1. AHIからデバイス入力イベントを受け取る。
2. デバイス識別子、入力コード、押下／解放などをイベントとして正規化する。
3. 入力イベントをアプリ側へ渡す。
4. 修飾キー状態を更新する。
5. キーバインド規則を評価する。
6. 対象外入力は通常入力として扱い、変換対象は定義済みアクションに従って処理する。

**重要：** 通常入力の通過、入力抑制、置換を実現するための最終的な判断は、AHIのフック仕様と実機検証に依存する。上記の論理フローがそのまま非同期キュー処理だけで実装できるとは限らない。

## 4. 入力イベントの概念モデル

初期案として次の情報を想定する。実際の型や必須項目は設計・技術検証で確定する。

- デバイス識別子
- 入力コード（キー／ボタン等）
- イベント種別（押下／解放など）
- 時刻または順序情報（必要性・取得方法は要検討）
- 元イベントに関する必要最小限の情報

入力内容をログへ無制限に記録しない。診断ログの範囲と保持方法は別途定義する。

## 5. 修飾キーの論理仕様

- 複数デバイスの修飾キー状態を、バインド評価で共有できる構成を目指す。
- 押下・解放の状態管理は、デバイスごとの物理状態と論理的な共有状態を区別する必要がある。
- 同じ修飾キーを複数デバイスで押した場合、片方だけ解放した場合、デバイス切断時の状態解除は未確定であり、設計判断とテストで決定する。

## 6. エラー・異常系

最低限、次のケースを設計・検証対象とする。

- デバイスが見つからない、または再接続された。
- 入力イベントの押下／解放が不整合になる。
- キューが処理に追いつかない。
- 設定ファイルに誤りがある。
- AHIの初期化またはフック登録に失敗する。
- アプリが終了・再起動する際に論理的なキー押下状態が残る。

異常時の具体的な復旧方法と安全側の挙動は未確定。

## 7. 未確定事項

- 入力を通過させるか抑制するかの決定タイミング。
- AHIコールバック内で必要な処理と許容時間。
- イベントキューの実装方式と同期方式。
- デバイス識別子の永続性。
- バインドの優先順位と競合解決。
- 修飾キーの共有状態モデル。
- 性能目標と計測方法。
